新機能「$ARGUMENTS」の開発を開始します。

## フェーズ0: 準備（サイレント実行）

以下を静かに実行してください（ユーザーへの報告は最後にまとめて）:

1. 機能名 `$ARGUMENTS` と本日の日付（YYYYMMDD）を確認
2. ステアリングディレクトリ: `.steering/{日付}-{機能名}/`
3. `CLAUDE.md` を読み、アーキテクチャ・規約を理解
4. brainstorm.md が存在するか以下の優先順位で確認
   - まず `.steering/{日付}-{機能名}/brainstorm.md` を確認
   - 次に `.steering/` 直下で最新の `{YYYYMMDD}-explore/brainstorm.md` を確認
   - どちらかが**存在する場合**: 課題感・有力候補・設計アイデアを把握してインプットとして保持
   - **存在しない場合**: スキップ
5. Grep / Glob で今回の機能に関連する既存コードとパターンを調査

調査完了後、以下を簡潔に報告してください:

- 参照した brainstorm.md の有無と要点
- 関連する既存コード・再利用できるパターン

その後、ユーザーに確認してください:

> 「調査が完了しました。requirements.md の作成に進みますか？」

## フェーズ4: 実装

### 実装モードの選択 🔀

実装を始める前に、ユーザーに実装モードを確認してください:

> 「実装を開始します。どちらのモードで進めますか？
>
> **[A] 写経モード**（学習目的）
>
> - Claude がコードを提示し、あなたが手で打ち込む
> - コードが頭に入りやすく、疑問をその場で解消できる
>
> **[B] 通常実装モード**（スピード優先）
>
> - Claude が直接ファイルを編集・実装する
> - 速い。動作確認に集中したい場合に向いている」

---

### [A] 写経モードの進め方

1. 「▶ フェーズ X の写経コードを提示します」と宣言する
2. そのフェーズのタスクを実装したコードを提示する
   - ファイルごとに分けて、どこに書くかを明示する
   - 重要な部分には「ここがポイント: [一言説明]」を添える
3. あなたがコードを手で打ち込む
4. 打ち込みながら疑問が出たら気軽に質問する（Claude がその場で答える）
5. 打ち込み完了したら `done: フェーズX` と入力する
6. Claude が実装をレビューし、問題なければ次フェーズのコードを提示する

**ルール**: コピペ禁止。意味が分からなくても打ち込んで OK。疑問は後から質問できる。

---

### [B] 通常実装モードの進め方

1. tasklist.md のフェーズ順に Claude が実装を進める
2. 各タスク完了時に `tasklist.md` の `[ ]` を `[x]` に更新する
3. フェーズ完了ごとに実装内容を簡潔に報告し、次フェーズに進む確認を取る

## フェーズ6: 品質検証

承認後、以下のコマンドを実行してください。

**バックエンド変更がある場合:**

```bash
cd backend && npm run test && npm run lint && npm run build
```

**フロントエンド変更がある場合:**

```bash
cd frontend && npm run lint && npm run build
```

**Prisma スキーマ変更がある場合:**

```bash
cd backend && npx prisma generate
```

失敗した場合は修正し、再実行してください。

### コミット提案 📝

全チェックがパスしたら、以下の形式でコミット分割案を提案してください:

> 「品質検証がすべてパスしました。以下のコミット分割を提案します。
>
> 1. `feat: [変更内容の概要]` — [対象ファイル群]
> 2. `feat: [変更内容の概要]` — [対象ファイル群]
> 3. `chore: [変更内容の概要]` — [設定・マイグレーションなど]
>
> このまま進めますか？」

コミットはユーザーの確認を得てから実行すること。
