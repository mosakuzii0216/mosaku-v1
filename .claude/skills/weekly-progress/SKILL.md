# 週次進捗ログ更新スキル

`docs/progress.md` の先頭に新しい週次エントリを追加し、合わせて `docs/project-plan-2026.md` の状況列を最新化する。

## 起動タイミング

- 毎週末（金曜 / 土曜 / 日曜）
- リリース・大型 spec 完了直後
- ユーザーが `/weekly-progress` を叩いたとき

## 前提

- 進捗ログの粒度は**週次**。「今日やったこと」より「この1週間で起きたこと」を集約する
- 計画書（`docs/project-plan-2026.md`）は方針・計画を、進捗ログ（`docs/progress.md`）は**実際に何が起きたか**を記録する役割分担を守る
- スキル単独でコミットまでは行わない。**必ずユーザーに diff を見せて確認を取ってから** `git add` / `git commit` を提案する

---

## 手順

### Step 1: 入力情報を集める

並列で以下を取得する：

1. **前回エントリの日付を `docs/progress.md` から特定**
   - 既存の `## YYYY-MM-DD` 見出しの最新を読み取る
   - 初回（既存エントリなし）なら過去7日分を対象にする
2. **前回エントリ以降の git log を取得**
   ```bash
   git log --since="<前回日付>" --pretty=format:"%h %s" --no-merges
   ```
3. **spec の完了状況を集計**
   ```bash
   for f in .kiro/specs/*/spec.json; do
     jq -r '[input_filename, .phase] | @tsv' "$f"
   done
   ```

   - `phase` が `completed` / `implementation-validated` のものを「完了」として扱う
4. **mosaku-brand-theme のような直近大型 spec の `tasks.md` 完了率**を `grep -c "\- \[x\]"` 等で取得（未完了 spec のみ）
5. **CLAUDE.md / steering ファイルの最終更新日**を `git log -1 --format=%ai` で確認（古ければ Step 4 でリマインド）

### Step 2: 差分を要約する

集めた情報から以下を抽出：

- **今週やったこと**: 完了 spec / 主要コミット（feat / fix / refactor を優先、docs / chore は省略可）/ 意思決定
- **来週の予定**: 進行中 spec の残タスク / Phase 1 直近タスク（`docs/project-plan-2026.md` から拾う）/ ユーザー会話で言及された計画
- **ブロッカー・懸念**: 未完了テスト / pre-push 失敗 / 仕様承認待ち等。なければ「なし」
- **メモ**: テーマ数・テスト数・FCP・コミット数等の数字や所感

> **要約原則**: コミットメッセージをそのまま転記しない。**何が前進したか**を一段抽象化して書く。

### Step 3: `docs/progress.md` に新エントリを追加

- 挿入位置: ファイル冒頭の `## エントリフォーマット` セクションの**直後**（`---` の次の行）
- フォーマットはファイル冒頭のフォーマット定義に厳密に従う
- 見出し: `## YYYY-MM-DD（フェーズ名 / 状況サマリ）`
  - フェーズ名は現在地（例: `Phase 1 ドッグフーディング中` / `Phase 2 運用フロー整備中`）
  - 状況サマリは1行（例: `mori テーマ完了 / Sentry導入着手`）

### Step 4: `docs/project-plan-2026.md` の状況列を更新

- Phase 1 以降の表に「状況」列が存在する → spec.json と突き合わせて `⬜` → `✅` に変える
- 完了 spec が計画外（4月追加ボーナス枠）なら、対応する月のセクション（5月〜12月）に追記する
- ファイル冒頭の `最終更新: YYYY-MM-DD` を今日の日付に更新する
- **計画自体（テーマ数 / 時間配分等）は勝手に変更しない**。変更が必要なら Step 5 でユーザーに伺う

### Step 5: ユーザーに確認

以下をまとめて提示：

1. `docs/progress.md` に追加したエントリの内容（diff ではなくレンダリング後を見せる）
2. `docs/project-plan-2026.md` で更新した状況列（diff のサマリ）
3. **計画変更の提案がある場合のみ**: 「テーマ作成が予定より遅れているので 6月 +5 → +3 に下げますか？」等の質問

ユーザーが OK を出したら git diff を見せて、コミット案を提示する：

- コミット 1: `docs: 週次進捗ログを YYYY-MM-DD 時点に更新`
- コミット 2（状況列の変更がある場合）: `docs: project-plan-2026.md の進捗状況を更新`

> **重要**: ユーザーが明示的に「コミットして」と言うまで `git commit` は実行しない。

---

## やらないこと

- **新規 spec の作成・承認**: `/kiro:spec-init` 等は別スキルの責務
- **コードの変更**: ドキュメントのみ更新する
- **steering ファイルの更新**: `/kiro:steering` の責務
- **要約の捏造**: git log にも spec.json にも痕跡がない作業は書かない（ユーザーが口頭で言及した内容のみ会話履歴から拾う）

---

## エラー時の挙動

- `docs/progress.md` が存在しない → ユーザーに「初回エントリとして作成しますか？」と確認
- `docs/project-plan-2026.md` の状況列が見つからない → 進捗ログのみ更新し、計画書更新はスキップしてユーザーに報告
- git log が空（前回から新規コミットなし）→ 「進捗なしエントリでも追加しますか？」と確認
