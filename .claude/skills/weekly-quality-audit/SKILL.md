# Weekly Quality Audit

週に一度、**ESLint と tsc が見られない領域**の品質負債を 1 つ返済する。
検出は機械的なスクリプトに委譲し、**安全性とスコープの小ささ**を最優先する。

## 前身からの変更点（重要）

このスキルは `daily-refactor`（毎日コミットを維持するための低優先度リファクタリング）を
再定義したもの。変更の理由は以下の 2 点。

1. **毎日コミットという目的は既に達成されている。** 直近 30 日のコミット 51 件のうち
   refactor は 5 件で、実際の主力は docs / fix / feat。リファクタリングをひねり出す
   動機が無くなった。
2. **旧スキルの上位カテゴリは「枯れた」のではなく、そもそも自動化で潰れていた。**
   未使用 import・`any`・`no-unsafe-*`・`console.log` は ESLint と tsc が pre-push
   フックと CI で常時ゼロに強制している。構造上ゼロにしかならない領域を毎日
   スキャンしていたため、候補が出ないのは当然だった。

そこで主戦場を「**機械が判定できず人間の判断が要る負債**」へ移し、頻度を週次に落とす。

## 対象とする変更カテゴリ

優先度が高いものから順に。**この順番でしか作業しない**。

1. **Lint / 型エラーの残渣** — 出ていれば何より先に潰す（通常はゼロ）
2. **テストが無い実装ファイルへのテスト追加** — 行数が多いものほど未検証ロジックが多い
3. **重複ロジックの共通化** — 複数ファイルに散った同一処理をユーティリティへ集約
4. **巨大ファイルの分割** — 振る舞いを変えない「移動」に限る
5. CLAUDE.md 規約に違反するコメントの整理（WHAT を説明するコメント、死語化したコメント等）
6. マジックナンバー / リテラルの定数化
7. 変数・関数名の明確化（省略名の展開など）
8. 単純な条件式の簡略化
9. 解決済み TODO / FIXME コメントの削除

カテゴリ 2 は成果物が `test` コミットになる。これは想定内で、監査の正当な成果とみなす。

## 手順

### 1. 候補を機械的に列挙する

カレントディレクトリで以下を実行する：

```bash
bash .claude/skills/weekly-quality-audit/scripts/find-candidates.sh
```

出力されるセクション：

| セクション           | 内容                                                                      |
| -------------------- | ------------------------------------------------------------------------- |
| `LINT_TYPE_GATE`     | ESLint / tsc の残渣。**空であることが正常**                               |
| `UNTESTED_FILES`     | テストが隣に無い実装ファイル（行数降順）                                  |
| `LARGE_FILES`        | 閾値（既定 300 行）を超えたファイル                                       |
| `DUPLICATE_HINTS`    | 2 ファイル以上に現れる同一実装行                                          |
| `WHAT_COMMENTS_HINT` | WHAT コメント候補                                                         |
| `MAGIC_NUMBERS`      | 定数化を検討すべき数値リテラル                                            |
| `RECENT_AUDIT_FILES` | **avoid リスト**（直近 14 日の refactor / test コミットで触ったファイル） |

環境変数 `EXCLUDE_DAYS` / `LARGE_FILE_MIN` / `TOP_N` で閾値を調整できる。

### 2. 候補を選定する

以下の **すべての制約** を満たすものを選ぶ：

- avoid リストに含まれていない
- 1 つのテーマに収まる（例: 1 ファイルへのテスト追加、1 箇所の重複共通化）
- 対象ファイル数が **1〜3 ファイル** に収まる
- 変更行数の目安：
  - テスト追加 … 上限なし（テストコードは対象外）
  - 純粋なリファクタリング … 実装側 **±50 行以内**
  - ファイル分割 … **±150 行以内**（純粋な移動行はカウントしない）
- 影響範囲のテストがすでに存在する（または今回追加する）

候補が見つからない場合は **「対象なし」とレポートして終了** する。無理にひねり出さない。

### 3. 変更を加える

- **ロジックの変更・バグ修正・機能追加は絶対にしない**
- ファイル分割は「振る舞いを変えない移動」に限る。移動ついでの書き換えをしない
- 1 コミット 1 テーマを徹底する。複数のカテゴリを混ぜない
- 周辺のリファクタリングを「ついでに」やらない

**テストを追加する場合の例外**：実装の挙動は一切変えない。テストを書いていて実装の
バグを見つけたら、**修正せずレポートに記録**して人間の判断を仰ぐ。バグ修正は監査の
スコープ外。

### 4. テストを実行する

変更後、必ず影響範囲のテストを実行する：

```bash
bash .claude/skills/weekly-quality-audit/scripts/run-affected-tests.sh <変更ファイル...>
```

すべて緑になることを確認する。落ちたら変更を取り下げてレポートに記録する。

### 5. レポートを出力する

対話実行では**コミットせず**レポートを出して人間の確認を待つ。
定期実行（無人）では後述の「無人実行モード」に従い、PR まで作る。

以下の形式で出力する：

```
## 変更意図
（この監査の目的を 1〜2 行で。例: 「未検証だった theme.service にテストを追加し回帰を検出可能にする」）

## 変更内容
- <ファイル名>:<行番号> — <変更の説明>
- ...

## 影響範囲のテスト結果
（実行したコマンドと結果。例: `run-affected-tests.sh backend/src/theme/theme.service.ts` → PASS）

## 発見したが手を出さなかったこと
（下記「記入基準」に従う。本当に何も無いときだけ「なし」）

## コミットメッセージ（案）
<type>(<scope>): <変更内容の要約>（<件数>件）
```

#### 「発見したが手を出さなかったこと」の記入基準

この節は**やり残しの申告欄**であり、空にできる条件は厳しい。以下を必ず書く。

- **カバーしきれなかった範囲。** テストを追加した場合は、対象ファイルの
  public メソッド／export された関数を列挙し、**カバーしたもの**と
  **カバーしなかったもの**を明示する。1 つでも未カバーなら「なし」とは書けない
- 実装の疑わしい挙動（修正はしない。記録だけする）
- スコープ制約で見送った候補

**「なし」と書いてよいのは、対象ファイルを全てカバーし、かつ疑わしい点も
見つからなかった場合だけ。** 判断に迷ったら書く側に倒す。

> なぜこの基準があるか: 2026-08-16 の無人実行で、8 つある public メソッドの
> うち 7 つしかテストしていないのに「なし」と報告した実例がある。しかも
> 最大のメソッド（`findMany`、検索フィルタを含む）が漏れていた。レビュー側も
> これを見抜けず「実装の全分岐と正確に一致」と要約して承認した。
> **不正確な申告は「検証済み」という誤った記録だけを残す**ため、実害が無い
> 変更であっても許容しない。

## コミットメッセージ規約

形式: `<type>(<scope>): <変更内容>（<件数>件）`

- **type**: テスト追加なら `test`、それ以外は `refactor`
- **scope**: `backend` / `frontend` / `auth` / `memo` / `tag` などのコンポーネント名。
  テスト中心なら `backend/test` のように細分化してよい
- **件数**: 警告解消件数や置換箇所数を末尾に括弧書きで添える（追跡しやすくするため）

実例（このリポジトリの過去コミットより）：

- `refactor(frontend/feedback): メッセージ最大文字数 1000 を MESSAGE_MAX_LENGTH 定数に括り出し（4件）`
- `refactor(backend/dashboard): 1日のミリ秒 24*60*60*1000 を MS_PER_DAY 定数に括り出し（2件）`
- `refactor(memo/test): memo.service.spec.ts から未使用の import と変数を削除`

## 制約（強い順）

1. **ロジック変更・バグ修正・機能追加は禁止** — 純粋な品質返済のみ
2. **テストは必ず実行**して緑を確認する。実行しないままレポートを出さない
3. **avoid リスト** に含まれるファイルには触らない
4. **対話実行ではコミットしない** — レポートを出してユーザーの確認を待つ。
   無人実行は例外で、PR を作るところまで進める（「無人実行モード」参照）
5. **main へ直接 push しない** — 無人実行でも必ずブランチ + PR を経由する
6. 仕様承認フロー（OpenSpec）は不要（既存の振る舞いを変えないため）

## 無人実行モード（定期実行）

毎週金曜にクラウドの定期エージェントから起動される。人間がその場にいないため、
対話実行との違いを明示する。

### 対話実行との差分

|                | 対話実行           | 無人実行                                     |
| -------------- | ------------------ | -------------------------------------------- |
| 候補の選定     | 迷ったら人間に聞く | **聞かずに最上位の候補を1つ選ぶ**            |
| 判断に迷う変更 | 相談する           | **やらない**（レポートに候補として書き残す） |
| 成果物         | レポートのみ       | ブランチ + コミット + PR                     |
| 候補ゼロのとき | 「対象なし」と報告 | **何も作らず終了**（空 PR を作らない）       |

### 手順

1. 通常の手順 1〜4 を実行する（候補列挙 → 選定 → 変更 → テスト）
2. **ブランチを切る**：`chore/weekly-audit-YYYY-MM-DD`
3. コミットメッセージ規約に従ってコミットする
4. PR を作成する。**PR 本文にはレポート全文（手順 5 の形式）をそのまま入れる**
   — GitHub Actions がこれを Slack へ転送するため、本文が通知の中身そのものになる
5. PR タイトルはコミットメッセージと同じにする

### 無人実行で特に守ること

- **不確実なら手を出さない。** 人間が止められないので、対話実行より保守的に倒す。
  「テストが緑だが挙動が変わったか自信が無い」なら破棄してレポートに記録する
- **候補をひねり出さない。** ゼロなら PR を作らずに終わる。空振りの週があってよい
- **テストが落ちたら PR を作らない。** 変更を破棄し、その事実をレポートに残す
- **main へ push しない。** 必ずブランチを切る（branch protection は admin bypass で
  通ってしまうので、規約側で禁じる）
- **PR を作ったらそこで終了する。** 以下は指示されていない限り行わない:
  - 追加のスケジュール／check-in の登録（自分を再起動する予約を作らない）
  - PR の購読・CI の追跡・マージまでの見届け
  - プッシュ通知の送信（通知は audit-notify.yml が Slack へ送る。二重になる）

  > なぜ: 2026-08-16 の実行で、指示していない「1 時間ごとに自分を再予約する
  > トリガー」が作られた。停止条件が「PR が merge か close されるまで」だったため、
  > PR を放置すると無期限に再予約が続く状態になっていた。週次で回す前提では
  > 実行のたびにこれが増えうる。CI とマージの面倒は GitHub 側の仕組みが見る。

### 通知経路

PR の作成をトリガーに `.github/workflows/audit-notify.yml` が Slack へ通知する。
監査エージェント自身は Slack を叩かない（クラウド側に webhook URL を置かないため）。

## スクリプト一覧

- `scripts/find-candidates.sh` — 候補を機械的に列挙
- `scripts/check-recent-files.sh` — 直近 N 日の refactor / test コミットで触ったファイル一覧（avoid リスト用）
- `scripts/run-affected-tests.sh` — 変更ファイルから影響範囲のテストを実行

### スクリプト実装上の注意（過去に踏んだ地雷）

- **テスト絞り込みに `--testPathPattern` を使わない。** jest は受け付けるが vitest 4 は
  フラグ自体を知らず `CACError: Unknown option` で即死する。両者に共通する
  **位置引数**で絞り込むこと。
- **`rg -t tsx` は存在しない。** `-t ts` が `*.tsx` も含む。指定するとエラー終了して
  検出結果が黙ってゼロ件になる。
- **モノレポではルートに `tsconfig.json` が無い。** ルートだけを見て諦めると型チェックを
  丸ごと取りこぼす。直下のワークスペースを辿ること。
