# Implementation Plan

## 並行実行ガイド

- **Task 1（基盤）→ Task 2 / Task 5 → Task 3 → Task 4** の順を基本とする。
- Task 5（フロント）は API 契約（design.md の AuthController API Contract）にのみ依存するため、バックエンド着手と並行して進められる `(P)`。
- Task 2（MailModule）は Task 1 で追加する ConfigService getter（`resendApiKey` / `mailFrom`）に依存するため、Task 1 完了後に着手すること。

- [x] 1. バックエンド基盤の整備（環境変数・定数・エラー定義）
- [x] 1.1 環境変数と ConfigService getter を追加
  - メールプロバイダ API キー（`RESEND_API_KEY`）と送信元（`MAIL_FROM`）を環境変数から読み込む getter を追加する
  - リセット URL ベースを環境変数から読み込み、未設定時はフロントエンド URL から確定画面パスを導出する getter を追加する
  - 追加した全環境変数（キー・送信元・URL ベース・throttle 上書き）を `.env.example` に dev 既定値・本番値の注記付きで記載する
  - _Requirements: 6.1, 6.2, 6.3_

- [x] 1.2 エラーコード・Refresh Token revoke 理由・レート制限設定を追加
  - トークン期限切れを表す新しいエラーコードを追加する
  - パスワード再設定起因のセッション無効化を区別する Refresh Token revoke 理由を追加する
  - パスワードリセット要求・確定向けのレート制限設定（既定 15 分 5 回、環境変数で上書き可）を既存設定と同形式で追加する
  - _Requirements: 4.3, 5.4_

- [x] 2. メール送信基盤（MailModule）の実装
- [x] 2.1 (P) Resend ラッパとして MailService を実装
  - 起動時に API キーの設定有無を判定し、未設定なら警告ログを出して起動を継続する（OAuth Strategy 未設定時と同じ挙動）
  - リセット URL を含む日本語の件名・本文のメールを登録メールアドレス宛に送信する処理を実装する
  - 送信失敗（SDK のエラー返却・例外の両方）を内部で握り潰し、`feature_area: 'auth'` タグ付きで Sentry に記録し、呼び出し側へ例外を伝播しない
  - 未設定・失敗時は送信せず結果のみを返し、要求フローのレスポンスに影響を与えないことを保証する
  - Task 1.1 の ConfigService getter（API キー・送信元）に依存する
  - _Requirements: 2.1, 2.3, 2.4, 2.5, 6.1, 6.4, 6.5_

- [x] 2.2 MailService の単体テストを追加
  - 未設定時に送信をスキップし警告ログを出して例外を投げないことを検証する
  - 送信失敗時に Sentry へ記録しつつ例外を投げないことを検証する
  - _Requirements: 2.4, 2.5, 6.4_

- [x] 3. パスワードリセットのドメインロジック（PasswordResetService）の実装
- [x] 3.1 リセット要求ロジックを実装
  - 暗号論的に安全なランダムトークンを生成し、そのハッシュ値と発行時刻 + 1 時間の有効期限を保存する
  - 平文トークンは永続化せず、再要求時は既存トークン・期限を上書きして旧トークンを無効化する
  - ユーザー不在・OAuth 専用アカウント（パスワード未設定）の場合は発行も送信も行わず例外も投げない（列挙一貫性）
  - 平文トークンへ変換したリセット URL を構築し MailService へ送信を委譲する
  - 各処理を AppLogger で記録する（メール平文・トークンは出力しない）
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.5, 2.2, 3.2_

- [x] 3.2 リセット確定ロジックを実装
  - 受領トークンをハッシュ化して保存済みハッシュと照合し、不一致・未設定は無効トークンエラーを返す
  - 有効期限を過ぎている場合は期限切れエラーを返し、いずれの失敗時もパスワードを変更しない
  - 全検証成功時に新パスワードを既存の bcrypt 規約でハッシュ化して保存し、トークン・期限を null にクリアする
  - 確定成功時に当該ユーザーの既存 Refresh Token を全て無効化する
  - 予期せぬ失敗は `feature_area: 'auth'` タグ付きで Sentry に記録する
  - _Requirements: 4.1, 4.2, 4.3, 4.6, 5.1, 5.2, 5.3, 5.5, 6.5_

- [x] 3.3 PasswordResetService の単体テストを追加
  - 要求：存在ユーザーでトークンハッシュ＋期限が保存される／再要求で上書きされる／OAuth・不在で副作用なく例外も投げない
  - 確定：正常確定でパスワード更新・トークンクリア・Refresh Token revoke が行われる／不一致・使用済みで無効トークンエラー／期限切れで期限切れエラー
  - _Requirements: 1.1, 1.3, 1.4, 4.2, 4.3, 5.1, 5.2, 5.3, 5.5_

- [x] 4. AuthController のエンドポイント結線とリクエスト検証
- [x] 4.1 要求・確定エンドポイントを公開して service へ委譲
  - 既存の要求エンドポイントを本実装化し、TODO とユーザー検索のみの実装を service 委譲へ置き換える
  - 確定エンドポイントを新設し、トークンと新パスワードを受けて確定処理へ委譲する
  - 両エンドポイントを `@Public()` として公開しつつパスワードリセット用レート制限を適用する
  - 新パスワードを既存の password-strength バリデータで検証し、強度不足はバリデーションエラーを返す
  - 要求エンドポイントは存在有無・送信成否に関わらず常に同一メッセージ・同一構造・同一ステータスを返す
  - _Requirements: 3.1, 3.3, 3.4, 4.4, 4.5, 5.4_

- [x] 4.2 認証フローの統合テストを追加
  - 要求エンドポイントが存在／不在／OAuth の 3 ケースで本文・ステータス・構造が同一であることを検証する（列挙対策の回帰防止）
  - 送信失敗注入時も要求エンドポイントが共通メッセージの 200 を返すことを検証する
  - 確定エンドポイントが有効トークンで実 DB のパスワードを更新し、無効・期限切れ・強度不足で該当エラーを返すことを検証する
  - _Requirements: 2.5, 3.1, 3.2, 3.3, 4.1, 4.3_

- [x] 5. (P) フロントエンドの確定画面と API 連携
- [x] 5.1 (P) リセット確定 API クライアントを追加
  - 既存の resetPassword と同じ makeRequest パターンで、トークンと新パスワードを確定エンドポイントへ送信する関数を追加する
  - _Requirements: 4.1_

- [x] 5.2 (P) リセット確定画面コンポーネントとルートを追加
  - メールリンク遷移先となる新ルートを追加し、URL クエリからトークンを取得する
  - 新パスワードと確認入力を受け付け、確定 API を呼び出し、成功時は完了表示とログイン導線、失敗時はエラー文言を表示する
  - 既存のログイン中変更 UI とは別ルート・別コンポーネントとし、既存リセットフォームのスタイル慣例を踏襲する
  - _Requirements: 4.1_

- [x] 5.3\* リセット確定画面の UI/E2E テストを追加
  - トークン付き URL での表示 → 新パスワード入力 → 確定 → ログイン導線表示の一連を検証する
  - トークン欠落 URL でのエラーハンドリング表示を検証する
  - _Requirements: 4.1_
