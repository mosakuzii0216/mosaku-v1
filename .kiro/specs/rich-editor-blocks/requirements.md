# Requirements Document

## Project Description (Input)

リッチエディタブロック第1波（rich-editor-blocks）: Tiptap エディタを markdown 相当からリッチ表現へ拡張する。対象は4機能 — (1) コールアウト/カード（💡ポイント・⚠️注意などの枠付きブロック、カスタムノード）、(2) テキスト色・マーカー（蛍光ペン風ハイライト。生 hex ではなく CSS 変数のセマンティックカラーパレットとし、mori/umi/yoru/asa 全テーマの明暗で AA コントラストを担保）、(3) 表（テーブル挿入・編集）、(4) トグル（折りたたみブロック）。いずれもスラッシュコマンドから挿入可能にする。実装上の不変則: createEditorExtensions.ts（編集/公開表示の拡張セット単一情報源）への追加で公開ビュー（PublicMemoRenderer）との往復一致を構造的に担保し、prosemirrorText.ts の検索テキスト抽出とオフライン層の追随も必ずスコープに含める。本文は JSONB（Tiptap JSON）保存済みのため保存側スキーマ変更は不要。スコープ外: 画像アップロード・リンクカード（OGP）は第2波以降の別 spec、登録時ウェルカムメモのシードは後続 spec「welcome-memo-seed」。背景・決定事項は .kiro/steering/20260707-rich-memo-experience/brainstorm.md を参照

## Introduction

本仕様は、Mosaku のリッチテキストエディタ（TipTap 3.22 + StarterKit、`frontend/src/components/editor/`）を markdown 相当の表現力からリッチ表現へ拡張する第1波である。対象は **(1) コールアウト、(2) テキスト色・マーカー、(3) 表、(4) トグル** の4機能（以下「4機能」）で、いずれもスラッシュコマンドメニューから利用できるようにする。

Mosaku は「使いたくなるデザイン」を差別化軸とするプロダクトであり、本機能の色彩は生 hex の固定色ではなく **テーマ対応のセマンティックカラー** として提供する。「mori / umi / yoru / asa のどのテーマでも美しく発色し、可読性（WCAG AA）を落とさない」ことを差別化ポイントと位置づける（theme-immersive-world で確立した機械検証文化を踏襲）。

前提として content-jsonb-migration が完了済みであり、本文は Tiptap JSON（JSONB カラム）ネイティブで保存される。したがって保存側の DB スキーマ変更は不要である。また、編集（`RichTextEditor`）と公開表示（`PublicMemoRenderer`）は拡張セットの単一情報源を共有する構造が確立しているため、4機能もこの枠組みに乗せて編集・公開の描画一致を構造的に担保する。新ノード追加に伴い、検索テキスト抽出（フロントエンド `prosemirrorText.ts` / バックエンド `prosemirror-text.ts`）とオフライン層（IndexedDB 保存・オフライン検索）の追随を必須スコープとする。

本仕様は WHAT（ユーザーから見た挙動と品質基準）を定義し、HOW（TipTap 拡張の選定・カスタムノードのスキーマ設計・UI 実装方式）は design フェーズで決定する。

### スコープ外

- 画像アップロード（第3波の別 spec）
- リンクカード / OGP 展開(第2波の別 spec)
- 登録時ウェルカムメモのシード(後続 spec「welcome-memo-seed」)
- 本文保存の DB スキーマ変更（JSONB 移行済みのため不要）

### 用語定義

- **4機能**: 本仕様で追加するコールアウト・テキスト色/マーカー・表・トグルの総称。
- **コールアウト**: アイコンと枠付き背景で本文を強調する専用ブロック（例: 💡ポイント・⚠️注意）。
- **マーカー**: テキストに適用する蛍光ペン風の背景ハイライト装飾。
- **セマンティックカラー**: 生の hex/rgb 値ではなく意味名の識別子で本文へ保存され、実際の表示色は適用中テーマの CSS 変数が解決する色。
- **トグル**: サマリー行と折りたたみ可能な本文領域からなるブロック。
- **公開ビュー**: 共有リンク経由の読み取り専用メモ表示（`PublicMemoRenderer`）。
- **往復一致**: 編集で作成した本文 JSON が、保存・再読込・公開表示を経ても構造と表示を欠損なく維持すること。
- **提供テーマ**: 現行の和の4テーマ（mori / umi / yoru / asa）。

## Requirements

### Requirement 1: コールアウトブロック

**Objective:** メモを書くユーザーとして、💡ポイントや⚠️注意のような枠付きブロックで情報を強調したい。そうすれば見返したときに重要な箇所が一目で分かる、見栄えの良いメモを作れるから。

#### Acceptance Criteria

1. When ユーザーがスラッシュコマンドメニューから「コールアウト」を確定したとき, the エディタ shall アイコンと枠付き背景を持つコールアウトブロックをカーソル位置に挿入する。
2. The エディタ shall コールアウトのプリセット種別として少なくとも「ポイント（💡）」と「注意（⚠️）」を含む複数種別を提供する。
3. When ユーザーがコールアウトの種別を変更したとき, the エディタ shall 本文テキストを保持したままアイコンと配色のみを切り替える。
4. While キャレットがコールアウト本文内にあるとき, the エディタ shall 複数段落の入力とインライン装飾（太字・斜体・リンク・テキスト色/マーカー等）の適用を許可する。
5. The エディタ shall キャレットをコールアウトの外（直後の通常段落）へ移動する手段を提供し、キャレットがブロック内に閉じ込められる状態を作らない。
6. The エディタ shall コールアウトブロックを本文ごと削除する手段を提供する。
7. While いずれの提供テーマが適用されているとき, the コールアウト shall 本文テキストとコールアウト背景のコントラスト比 4.5:1（WCAG AA）以上を維持する。

### Requirement 2: テキスト色・マーカー（テーマ対応セマンティックパレット）

**Objective:** メモを書くユーザーとして、大事な言葉を文字色や蛍光ペンで目立たせたい。そうすればどのテーマでも美しく読みやすい、メリハリのあるメモを書けるから。

#### Acceptance Criteria

1. When ユーザーがテキストを選択し色選択 UI からテキスト色を選んだとき, the エディタ shall 選択範囲へそのテキスト色を適用する。
2. When ユーザーがテキストを選択し色選択 UI からマーカー色を選んだとき, the エディタ shall 選択範囲へ蛍光ペン風の背景ハイライトを適用する。
3. The 色選択 UI shall テキスト色・マーカーそれぞれに4色以上のセマンティックカラーを提供する。
4. When ユーザーが適用済み範囲に対して「デフォルトに戻す」操作を行ったとき, the エディタ shall テキスト色/マーカーを除去して既定の表示へ戻す。
5. The エディタ shall 適用した色をセマンティック識別子として本文 JSON に保存し、生の hex/rgb 値を本文 JSON に保存しない。
6. When ユーザーがテーマを切り替えたとき, the システム shall 本文 JSON を変更することなく、適用済みのテキスト色/マーカーを新テーマの対応色で描画する。
7. While いずれの提供テーマが適用されているとき, the テキスト色 shall そのテーマの本文背景に対してコントラスト比 4.5:1（WCAG AA）以上を満たす。
8. While いずれの提供テーマが適用されているとき, the マーカー shall ハイライト背景の上のテキストがコントラスト比 4.5:1（WCAG AA）以上を満たす配色で描画される。
9. If 適用中テーマがセマンティックカラーの CSS 変数を定義していないとき, then the システム shall 可読性を確保できる既定色へフォールバックして描画する。
10. The テストスイート shall 全提供テーマ×全セマンティックカラーの組み合わせについて AA コントラスト充足を機械検証する。

### Requirement 3: 表（テーブル）

**Objective:** メモを書くユーザーとして、行と列で情報を整理した表を挿入・編集したい。そうすれば比較や一覧を含む構造的なメモを書けるから。

#### Acceptance Criteria

1. When ユーザーがスラッシュコマンドメニューから「表」を確定したとき, the エディタ shall ヘッダー行を持つ複数行×複数列の表をカーソル位置に挿入する。
2. While キャレットが表のセル内にあるとき, the エディタ shall セル内テキストの入力・編集とインライン装飾の適用を許可する。
3. The エディタ shall 表に対する行の追加・削除および列の追加・削除の操作手段を提供する。
4. The エディタ shall 表全体を削除する操作手段を提供する。
5. When キャレットがセル内にある状態でユーザーが Tab / Shift+Tab を押したとき, the エディタ shall 次/前のセルへキャレットを移動する。
6. If 表の幅が表示領域の幅を超えるとき, then the エディタおよび公開ビュー shall ページ全体のレイアウトを崩さずに全列へアクセスできる表示（横スクロール等）を提供する。

### Requirement 4: トグル（折りたたみブロック）

**Objective:** メモを書くユーザーとして、詳細や補足を折りたたんで隠しておきたい。そうすれば長いメモでも全体の見通しを保てるから。

#### Acceptance Criteria

1. When ユーザーがスラッシュコマンドメニューから「トグル」を確定したとき, the エディタ shall サマリー行と本文領域を持つトグルブロックを開いた状態で挿入する。
2. When ユーザーがトグルの開閉操作を行ったとき, the エディタ shall 本文領域の表示/非表示を切り替える。
3. While トグルが閉じているとき, the エディタ shall サマリー行のみを表示する。
4. The トグル shall サマリー行のテキスト編集と、本文領域への複数ブロック（段落・リスト等）の配置を許可する。
5. When 公開ビューの閲覧者がトグルの開閉操作を行ったとき, the 公開ビュー shall 本文の編集を許可しないまま開閉表示を切り替える。

### Requirement 5: スラッシュコマンド統合

**Objective:** メモを書くユーザーとして、`/` から新しいリッチブロックも既存ブロックと同じ操作感で挿入したい。そうすれば覚えることを増やさずにリッチな表現へ手が届くから。

#### Acceptance Criteria

1. The スラッシュコマンドメニュー shall 既存コマンド群に加えて「コールアウト」「テキスト色」「マーカー」「表」「トグル」の項目を提供する。
2. When ユーザーが `/` に続けてクエリを入力したとき, the スラッシュコマンドメニュー shall 新項目についても日本語名・英語別名・読みによる絞り込みを提供する。
3. When ユーザーが「テキスト色」または「マーカー」の項目を確定したとき, the エディタ shall セマンティックカラーの選択 UI を提示し、選択された色を以降の入力テキストへ適用する。
4. When ユーザーが新項目のいずれかを確定したとき, the エディタ shall `/` とクエリ文字列を削除した上で対応する挿入または適用を実行する。
5. When ユーザーが挿入直後に Undo（Ctrl/Cmd+Z）を実行したとき, the エディタ shall 挿入前の状態へ戻す。
6. The スラッシュコマンドメニュー shall 既存のブロック挿入9コマンドとノートブック参照の挙動を変更しない。

### Requirement 6: 編集・公開表示の往復一致

**Objective:** メモを共有するユーザーとして、編集画面で作ったリッチな表現が公開ページでもそのまま再現されてほしい。そうすれば見せたい姿のまま人に届けられるから。

#### Acceptance Criteria

1. The フロントエンド shall 4機能のノード/マーク定義を、編集用エディタと公開ビューが共有する単一の拡張セット定義（`createEditorExtensions.ts`）へ追加する。
2. When 4機能を含むメモを公開ページで表示したとき, the 公開ビュー shall コールアウトの種別・テキスト色/マーカー・表の構造・トグルの内容を編集画面と同一の構造で描画する。
3. When 4機能を含むメモを保存して再度開いたとき, the エディタ shall 全ノード・マーク・属性を欠損なく復元する。
4. While 公開ビューが表示されているとき, the 公開ビュー shall トグルの開閉を除く編集操作を受け付けない。
5. The 公開ビュー shall セマンティックカラーを適用中テーマの定義で解決し、Requirement 2 と同一の可読性基準で描画する。

### Requirement 7: 検索テキスト抽出の追随

**Objective:** メモを探すユーザーとして、コールアウトや表の中に書いた言葉でも検索でメモを見つけたい。そうすればリッチ表現を使うほど検索に弱くなる事態を避けられるから。

#### Acceptance Criteria

1. When ユーザーがコールアウト本文・表のセル・トグルのサマリー/本文に含まれるテキストで検索したとき, the 検索機能 shall 該当メモを検索結果に含める。
2. The フロントエンドのテキスト抽出（`prosemirrorText.ts`） shall 4機能のノード内テキストを平文抽出結果に含める。
3. The バックエンドのテキスト抽出（`prosemirror-text.ts`） shall 4機能のノード内テキストを平文抽出結果（検索・一覧プレビュー等の用途）に含める。
4. While トグルが閉じた状態で保存されているとき, the 検索機能 shall 折りたたまれた本文テキストも検索対象に含める。
5. The テキスト抽出 shall テキスト色/マーカー適用済みテキストを通常テキストと同様に抽出する。
6. If 4機能のノードが本文 content 以外の場所（属性等）に表示テキストを保持する設計となったとき, then the テキスト抽出 shall そのテキストも抽出対象に含める。

### Requirement 8: オフライン層の追随

**Objective:** オフラインでも使うユーザーとして、電波がない場所で書いたリッチなメモも欠けることなく保存・同期されてほしい。そうすれば場所を選ばず安心してリッチ表現を使えるから。

#### Acceptance Criteria

1. When オフライン状態で4機能を含むメモを編集したとき, the オフライン層 shall 本文 JSON を欠損なくローカルへ保存する。
2. When 接続が回復したとき, the オフライン層 shall 4機能を含む本文を欠損なくサーバーへ同期する。
3. The オフライン検索 shall 4機能のノード内テキストを検索対象テキストに含める。
4. When オフライン保存されたメモを再表示したとき, the エディタ shall 4機能を編集時と同一の構造で復元する。

### Requirement 9: データ互換性と非回帰

**Objective:** 既存ユーザーとして、新機能が入っても今までのメモと書き心地がそのまま動き続けてほしい。そうすれば安心してアップデートを受け入れられるから。

#### Acceptance Criteria

1. The バックエンド API shall 4機能のノード/マークを含む本文 JSON を、既存の JSONB カラムと既存バリデーションの枠組みのまま受理し保存する（DB スキーマ変更なし）。
2. When ユーザーが4機能を含むメモを編集したとき, the 自動保存 shall 既存メモと同一の挙動（編集停止後の自動保存・保存状態インジケーター）で動作する。
3. If 本文に4機能を含まない既存メモを開いたとき, then the エディタ shall 従来どおりの表示・編集動作を維持する。
4. The エディタ shall 既存の Markdown input rules・ツールバー・ノートブック参照・チェックリスト等の既存機能の挙動を変更しない。
