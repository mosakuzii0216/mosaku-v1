> requirements（`requirements.md`・**未承認**）と既存コードベースの差分を分析し、design フェーズの判断材料を提供する。
> **本書は情報提供であり意思決定ではない。** 複数の実装アプローチを提示し、未知点は「Research Needed」として明示する。
>
> ⚠️ 注記: 本分析時点で requirements は `approved: false`。分析結果が要件の微修正（特に Req 6.5 の「適用中テーマ」解釈）を促す可能性があるため、承認前のギャップ分析として妥当。
> ✅ 追記（2026-07-08）: 上記の微修正候補は requirements へ反映済み — Req 6.5 を「`:root` 中立既定パレットで解決（公開ビューへのテーマ適用はスコープ外）」へ変更し、Req 2.10 の機械検証対象とスコープ外節も追随済み。

## 分析サマリー

- **土台は異常に良い。4機能を「差し込むだけ」の受け皿が既に3つ揃っている。** (1) `createEditorExtensions.ts` が編集/公開の単一情報源として確立済み、(2) FE/BE のテキスト抽出は content 再帰の汎用実装で **content にテキストを持つノードなら追加コードほぼゼロで自動追随**、(3) オフライン層の `searchableText` も同じ FE 抽出器に依存 → **抽出器1点の対応で Req7（FE/BE）と Req8.3 が同時に満たせる**。BE バリデータ（`IsProseMirrorDoc`）はノードタイプのホワイトリストを持たない構造チェックのみで、Req 9.1（DB/バリデーション変更なし）は既に成立している。
- **最大の新規開発は「セマンティックカラーの色体系そのもの」。** TipTap 拡張の導入・改造より、「4テーマ（明1・暗3、しかも背景が多ストップグラデ）× テキスト色/マーカー × 4色以上」で全て AA を満たす **色値の設計** が実質最重量。ただし AA 機械検証のインフラ（CSS パース + WCAG 計算 + worst-case 床合成）は `tokens.contrast.test.ts` に完成形があり、Req 2.10 はそのパターンの一般化で書ける。
- **公式拡張が使えるのは 表・色・マーカー・トグルの4つ、コールアウトのみ完全カスタムノード。** ただし該当パッケージ（table / text-style / highlight / details 系)は**全て未インストール**で、TipTap 3.x はパッケージ統合が行われた世代のため正確なパッケージ名/API の確認が design の必須リサーチ。
- **要注意の構造的衝突が2つ。** (1) `PublicMemoRenderer` は `pointer-events-none` で全クリックを殺しており、Req 4.5（公開ビューでのトグル開閉）と正面衝突する。(2) 公開ページにはテーマ機構が一切なく、Req 6.5 の「適用中テーマの定義で解決」は実質「`:root` 中立既定パレット（= Req 2.9 のフォールバック）で解決」という解釈の確定が要る。
- **総合規模 L（1〜2週間）／リスク中。** 新規 DB 変更ゼロ・確立済みパターン多数でリスクは抑えられているが、(a) TipTap 3.x パッケージ構成、(b) カスタムノードのキャレット操作性、(c) グラデ背景上の AA 検証戦略が未知点。

### 1.2 TipTap パッケージの導入状況（モノレポルートに hoist）

- **導入済み**: `core` / `starter-kit` / `extension-list`（TaskList/TaskItem）/ `extension-mention` / `extension-placeholder` / `extension-code-block-lowlight` / `suggestion` / `react` / `html` / `pm`。`extension-bubble-menu` / `extension-floating-menu` は推移的依存として存在（直接依存には未宣言）。
- **未導入（4機能に必要）**: table 系・text-style/color 系・highlight・details 系は**一切なし**。バージョンは 3.22.2 固定運用。
- 🟡 TipTap 3.x は拡張パッケージの統合・改名が行われた世代（例: `extension-list` に TaskList/TaskItem が同居）。table が `TableKit`、text-style 系が統合パッケージ、details の MIT オープンソース化状況など、**3.22.2 時点の正確なパッケージ名と API は design での要確認事項**。

### 1.3 テキスト抽出とオフライン層

- FE `utils/editor/prosemirrorText.ts` と BE `common/utils/prosemirror-text.ts` は同一ロジック: `text` ノード収集 + `hardBreak`→空白 + **`content` 配列の再帰**（ブロック間は空白区切り）。→ **content にテキストを持つ新ノードは両者とも無改修で抽出される**。attrs にテキストを持たせた場合のみ漏れる（Req 7.6 が予見している設計制約）。
- BE は保存/更新時に `contentText` 派生カラムを生成（`memo.service.ts:129,164`、`notebook.service.ts`）。4機能を含むメモは必ず新コード経由で保存されるため **既存データの backfill は不要**。
- オフライン層 `utils/offline/repository.ts:126,226` は `extractPlainText(snapshot.content)` で `searchableText` を生成し、content 自体は JSON パススルーで IndexedDB 保存 → Req 8.1/8.2/8.4 は構造的に既対応（**担保テストの追加が主作業**）。

### 1.4 バリデーション（BE）

- `IsProseMirrorDoc`（`common/utils/prosemirror-types.ts`）: `type:'doc'` + content が配列 + 各ノードが `type: string` を持つことのみ検証。**ノードタイプのホワイトリストなし** → 4機能のノード/マークは現行のまま受理される（Req 9.1 成立。受理を固定する回帰テストの追加のみ推奨）。

### 1.5 テーマ/CSS の2層構造とセマンティックカラーの不在

| 層       | 実体                                                                                                                                | 状態                                                                                                                                                 |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| シェル層 | `src/themes/shell/tokens.css`（`:root` 中立既定値 + `[data-theme='mori']`）を `index.css` が render-blocking import                 | umi/yoru/asa はコメント placeholder。**エディタ本文の色彩はこの層の管轄外**                                                                          |
| メモ面層 | `public/themes/{name}/{name}.css`（`.theme-root` + `--theme-bg/text-color/heading-color/accent-color/border-color`）を fetch ロード | **4テーマ全て実在**。ただしエディタ用セマンティックカラー変数（テキスト色/マーカー/コールアウト配色）は**未定義** → 4テーマ全 CSS への変数追加が必要 |

- 4テーマの `--theme-bg` はいずれも**多ストップの linear-gradient**（例: mori は深緑5ストップ）。「本文背景に対する AA」（Req 2.7）の検証は単色比較では成立せず、**全ストップ（または最明・最暗の両端）に対する worst-case 検証**が必要。
- **公開ページ（`PublicMemoPage`→`PublicMemoView`→`PublicMemoRenderer`）にはテーマ機構が皆無**（ニュートラル Tailwind + prose）。→ Req 6.5 は「`:root` に定義する中立既定パレット = Req 2.9 のフォールバック」が公開ビューの主経路になる、という解釈の確定が必要。
- エディタ本文は編集画面では `.theme-root .memo-content` 配下でテーマ化され、`prose`（Tailwind Typography）も同時に効いている → 新ブロック（table/details/callout）のスタイルは **prose のデフォルトスタイルとの共存設計**が要る。

### 1.6 AA 機械検証インフラ（再利用可能・完成形）

`src/themes/shell/tokens.contrast.test.ts` に以下が揃っている:

- CSS ファイルのブロック/変数パーサ（`findBlock` / `extractVar`）
- WCAG 2.1 準拠の `relativeLuminance` / `contrastRatio` / 半透明の床合成 `compositeOver`
- worst-case 床（白 #ffffff）との両端合成戦略、計算ユーティリティ自体の既知値セルフテスト

→ Req 2.10（全テーマ×全色の AA 機械検証）は、このユーティリティを共有化（or 複製）して `public/themes/*/*.css` を対象に一般化すれば新規発明なしで書ける。現状はテストファイル内へのインライン定義のため、**共有ユーティリティへの抽出 vs テストごとの複製**が design の小さな判断点。

## 3. 主要ギャップの深掘り（design で要決着）

### G-1. 公開ビューの `pointer-events-none` vs トグル開閉【構造衝突・Missing】

`PublicMemoRenderer.tsx:17` の `pointer-events-none` は「読み取り専用 = 一切の操作を殺す」思想で、Req 4.5「公開ビューの閲覧者がトグルを開閉できる」と正面衝突する。
→ 候補: (a) `pointer-events-none` を外し `editable:false` + Req 6.4 の「編集操作を受け付けない」を TipTap 側の責務に寄せる、(b) CSS でトグルの開閉ハンドルのみ `pointer-events: auto` を選択的復活、(c) 公開ビュー専用に details を native `<details>/<summary>` で描画。リンククリック（現状 `openOnClick: !editable` でクリック遷移を意図）との整合も含め、**「公開ビューで操作できるもの一覧」を design で棚卸しすべき**。

### G-2. セマンティックカラーの保存表現と公式拡張の改造【Missing・Req 2.5 の核】

公式の Color / Highlight は `style="color: #hex"` / `data-color="#hex"` として**生 hex を attrs に保存する**のがデフォルト = Req 2.5 に非準拠。
→ 有力な型: attrs にはセマンティック名のみ保存（例: `{ textColor: 'kasumi' }`）し、`renderHTML` で `data-text-color="kasumi"` を出力、CSS 側で `[data-text-color='kasumi'] { color: var(--editor-text-kasumi, <既定値>) }` と解決する。`var()` の第2引数 or `:root` 既定値が Req 2.9 のフォールバック（＝テーマ非適用の公開ビューの主経路）を兼ねる。公式拡張を `extend` するか、薄い自作 mark にするかは design の判断（§4 軸2）。

### G-3. グラデ背景上の AA 検証戦略【Unknown→設計必須・Req 2.7/2.8/2.10】

4テーマの本文背景は多ストップグラデで、テキスト色の AA は単色比較で判定できない。マーカーはさらに「マーカー背景×上のテキスト」のペアで、マーカー背景を半透明にするとテーマ背景との合成が絡んで検証が爆発する。
→ 候補: (a) **マーカー背景・コールアウト背景は不透明（テーマごとの実色）で定義**し、検証を「不透明背景×テキスト」に単純化する、(b) テキスト色はテーマ背景の**全グラデストップに対して** AA を検証する（既存テストの「両端合成」戦略の一般化）。色決めそのものが4テーマ×2種×4色以上（+コールアウト種別配色）で最低32ペア超になり、**本 spec の実質的な最重量作業**として design で色表を先に確定させるべき。

### G-4. コールアウトのノード設計と操作性【Missing + Unknown】

プロジェクト初のカスタムブロックノード。決めることは (a) スキーマ（`content: 'block+'`、種別は attrs、**ラベルテキストを attrs に置かない** — Req 7.6 回避）、(b) 種別変更 UI（NodeView 内蔵セレクタ vs バブルメニュー）、(c) キャレット脱出（文末コールアウトから Enter/ArrowDown で抜ける keymap。Gapcursor は StarterKit 同梱だが最終ブロック問題の実挙動は要検証）。ReactNodeViewRenderer 採用なら本プロジェクト初パターンとして design で契約を明文化する。

### G-5. TipTap 3.22.2 のパッケージ地図【Unknown・最初のリサーチ】

3.x はパッケージ統合世代（本リポでも TaskList/TaskItem が `extension-list` 同居）。table（TableKit?）・text-style 系（統合パッケージ?）・highlight・details（OSS 化の有無とパッケージ名）の**3.22.2 時点の正確な調達先と API** を design 冒頭で確定させる。全て 3.22.2 でバージョン固定できるかも要確認。

## 4. 実装アプローチ・オプション

全体としては「公式拡張の導入 + 単一情報源への追加（Extend）」と「カスタムノード/UI の新規作成（New）」の**ハイブリッド（Option C）がほぼ確定的**。判断が分かれるのは以下の4軸。

### 軸1: TipTap 拡張の調達

|     | A: 公式拡張を最大限利用（表/色/マーカー/トグル）+ コールアウトのみ自作                      | B: 全て自作カスタムノード                             |
| --- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| ✅  | スキーマ・キーボード操作・エッジケースの品質を公式に委譲。Tab 移動（Req 3.5）等が標準で付く | 依存ゼロ・完全制御                                    |
| ❌  | 3.x パッケージ地図の確認が必要（G-5）                                                       | 表のセル選択/行列操作の再発明は工数爆発・品質リスク大 |

→ **A を推奨**。B は表がある時点で現実的でない。

### 軸2: セマンティックカラーの保存表現（G-2）

|     | A: attrs にセマンティック名のみ + data 属性 + CSS 変数解決                                      | B: 公式のまま style に `var(--…)` 文字列を保存                                 |
| --- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| ✅  | JSON が意味論的にクリーン。CSS 変数名の変更が本文データに波及しない。Req 2.5/2.6 を構造的に充足 | 改造最小                                                                       |
| ❌  | 公式拡張の extend（renderHTML/parseHTML/commands）が必要                                        | CSS 変数名が本文 JSON に固定化 = 事実上の「生値」保存で Req 2.5 の趣旨に反する |

→ **A を推奨**。B は要件と矛盾するため実質選択肢でない（比較として明示）。

### 軸3: 色選択 UI の配置

|     | A: バブルメニュー（選択時）+ スラッシュサブメニュー（以降の入力へ適用）                                                                       | B: 固定ツールバー拡張 + スラッシュサブメニュー        | C: スラッシュのみ                                                                                    |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| ✅  | Req 2.1/2.2（選択範囲へ適用）と Req 5.3（以降の入力へ適用）を自然にカバー。`extension-bubble-menu` は推移的依存として既に node_modules に存在 | 既存ツールバー（RichTextEditor 内）の延長で実装が素直 | 実装最小                                                                                             |
| ❌  | バブルメニューは新 UI パターン（直接依存への昇格も必要）                                                                                      | 選択中の色適用導線としてはカーソル移動が遠い          | **Req 2.1/2.2 を満たせない**（スラッシュはキャレット位置発動で「選択したテキストへ適用」ができない） |

→ C は要件不充足。**A or B（併用含む）を design で決定**。表の行列操作 UI（Req 3.3）も同じバブルメニュー基盤に相乗りできるため、A はコールアウト種別変更（Req 1.3）・表操作と UI 基盤を共通化できる利点がある。

### 軸4: コールアウト/トグルの描画方式

|     | A: ReactNodeViewRenderer（React コンポーネント内蔵 UI）                                  | B: プレーンな renderHTML + CSS + 外部 UI（バブルメニュー/keymap） |
| --- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| ✅  | 種別セレクタ・開閉ボタンをブロック内に自然に置ける。公開ビューのトグル開閉も制御しやすい | NodeView 非依存でシンプル。往復一致の検証面が小さい               |

## 6. design フェーズへの推奨事項

### 推奨アプローチ（要 design 確定）

- 軸1=A（公式拡張最大活用）、軸2=A（セマンティック名保存 + CSS 変数解決）を推奨。軸3（色 UI 配置）と軸4（NodeView 採否）は UI 設計と合わせて design で決定。
- 実装順は「**パレット CSS + AA 検証（色表確定）→ 色/マーカー → 表/トグル → コールアウト → スラッシュ統合 → 追随テスト**」のように、最重量の色体系を先に固めると後続がブレない。
- Req 6.5 は「公開ビューは `:root` 中立既定パレットで解決する（テーマ非適用が仕様）」と解釈を明文化することを推奨（要件文の微修正候補）。→ **2026-07-08 反映済み**（Req 2.10 の検証対象・スコープ外節も追随）。

### Research Needed（design 冒頭で解消すべき未知点）

1. **TipTap 3.22.2 のパッケージ地図**（G-5）: table / text-style(color) / highlight / details の正確なパッケージ名・API・ライセンス（details の OSS 化）・3.22.2 での提供状況。
2. **Details の `editable:false` 挙動**: 公開ビューで開閉が動くか、開閉状態が doc（attrs）に書き込まれるか（書き込まれるなら公開ビューでの状態管理方法と Req 7.4 への影響）。
3. **`pointer-events-none` の解消方式**（G-1）: 公開ビューで許可する操作の棚卸しと安全な実装（リンククリックとの整合含む）。
4. **キャレット脱出の keymap 慣例**（G-4）: 文末コールアウト/トグルからの脱出（ArrowDown / Enter×2 / Mod-Enter）と Gapcursor の実挙動。
5. **マーカー/コールアウト背景の不透明化方針**（G-3）: AA 検証を単純化できるか。半透明にする場合の合成検証設計。
6. **prose（Tailwind Typography）との共存**: table / details / callout / mark に対する prose デフォルトスタイルの干渉範囲。
7. **mark の共存**: テキスト色 + マーカー + 既存装飾（bold 等）の同時適用時の JSON 構造と描画（Req 1.4 の「コールアウト内でのインライン装飾」含む）。
