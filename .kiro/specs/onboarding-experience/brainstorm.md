# ブレインストーミング - 2026-06-08

## セッションの文脈

- 出発点となった課題感: 6月末の友人10〜20人限定公開に向け、初回ログイン後の体験が「メモがありません＋作成ボタン」だけで、mosaku の武器（15テーマ・ノートブック・タグ・リッチエディタ・公開共有・PWA）が初回ユーザーに伝わらない。ある程度リッチなオンボーディングにしたい。
- 議論の流れ: 「初回に何を感じてほしいか」の優先順位づけ → 第一印象の作り方（A）→ 書き始めの橋渡し（B）→ 機能の伝え方（C）→ テーマ適用先のアーキテクチャ整合を確認して着地。

## 第一印象の優先順位（合意）

ユーザー選択: **A → B → C** の順

- **A「うわ綺麗！」**: テーマの美しさで掴む（最優先・差別化軸）
- **B「お、すぐ書ける」**: 迷わず書き始められる
- **C「機能いろいろあるじゃん」**: 機能を一通り知ってもらう（最後・軽く）

## 確定した設計方針

### A-1: テーマ選択から始める（参加型）

- 初回ログイン直後に「どの世界観にする？」とテーマギャラリーを表示し、15テーマから1つ選ばせる
- 選んだ瞬間にその世界観が反映される（＝自分で選んだ愛着、15テーマの存在を最初に提示）
- **スキップ可**（小さく「あとで」リンクを置く。目立たせないがデフォルトは選択を促す）

### B-1: 「ようこそノートブック」＋サンプルメモ

- 選択完了後、自動で「ようこそ」ノートブックを作成し、サンプルメモを1〜2枚シードする
- サンプルメモは選んだテーマで表示され、A の感動を本物のコンテンツで二度刺し
- サンプル自体が見出し・チェックリスト・コードブロック・スラッシュコマンドの**お手本**になり、C（機能ツアー）を吸収する
- 「何を書くか」のイメージが湧くよう、ある程度の内容量を持たせる
- 自由に編集・削除でき、押し付けがましくならないよう簡単に消せること

### C: サンプルメモとノートブックが吸収

- コーチマーク連打のツアーはしない
- 「ようこそノートブック」自体がノートブックという概念の説明になる
- サンプルメモの中身でエディタ機能を「説明」ではなく「お手本」で教える

### テーマ適用方式（アーキテクチャ整合）→ 解釈1で確定

- 前提: `useActiveTheme.ts` でテーマは `selectedNotebook?.theme || memo?.notebook?.theme || null` と解決され、**テーマはノートブック単位**。アプリ全体の共通テーマ概念は無い。
- **解釈1（採用）**: 選んだテーマを自動作成する「ようこそノートブック」に適用する。A-1（選択）と B-1（ようこそ＋サンプル）が「テーマ済みようこそノートブック」という1つの成果物に統合される。既存設計を壊さず実装が軽い。
- 解釈2（不採用・将来）: 選択テーマをユーザーのデフォルトテーマとして保存し新規ノートブック/INBOX にも適用。backend のユーザーフィールド追加（Prisma マイグレーション）＋適用ロジックが必要。友人公開後のフィードバック次第で別 Phase に。

## 有力候補（＝実装する機能）

**「リッチ・オンボーディング体験」**: 初回ログイン → テーマ選択（A-1, スキップ可）→ 選択テーマを適用した「ようこそノートブック」自動作成 → お手本サンプルメモをシード（B-1, C 吸収）。テーマはノートブック単位という既存設計に沿う（解釈1）。

## 実施メモ

- 選択した機能: リッチ・オンボーディング体験（spec 名候補: `onboarding-experience`）
- 次のステップ: `/kiro:spec-init` で起票し、cc-sdd フロー（requirements → design → tasks → impl）へ
- 設計フェーズで詰める技術論点:
  - 初回ログイン判定とオンボーディング完了フラグの保管先（localStorage か backend ユーザーフィールドか。PWA/複数端末を考慮）
  - 「ようこそノートブック」とサンプルメモのシード方法（フロントの既存 apiClient 作成 API か、backend 登録時シードか）
  - スキップ時にようこそノートブックを作るか／作らないか
  - サンプルメモの具体的な文面・枚数
