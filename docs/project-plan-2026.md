## 方針・前提

| 項目               | 決定事項                                                                         |
| ------------------ | -------------------------------------------------------------------------------- |
| 登録方式           | **招待制を永続維持**。招待コードをDMに含めて営業する形式                         |
| 権限モデル         | **ADMIN / USER の2種類のみ**（PREMIUMロール廃止）                                |
| 招待コード種別     | **通常コード**（1回使い切り）と**キャンペーンコード**（1コードでN名まで登録可）  |
| 収益化             | 友人フェーズまで完全無料。友人ヒアリング後にノートブック買い切りモデルを判断     |
| フィードバック     | アプリ内フォーム → Slack通知                                                     |
| ランディングページ | デザイン・テーマのショーケースを前面に出した視覚重視のLP                         |
| SNS営業チャネル    | **X（Twitter）** + **Instagram**（両方新規アカウント作成）                       |
| 差別化軸           | **ハイセンスなデザイン・テーマ数の多さ・ブランディングの雰囲気**                 |
| テーマ目標         | **50テーマ**（現在7、43追加。週5時間込みで現実的な数）                           |
| 障害対応           | Sentryエラー検知 → AIが自動で初期調査しSlack通知 → 必要なら即時対応              |
| 開発ペース         | **週5時間**（月約20時間、テーマ作成込み）                                        |
| 開発プロセス       | **cc-sdd（仕様駆動開発）**。全ての機能追加・修正は仕様定義→承認→実装の順で進める |

### Phase -1: cc-sdd導入・監査（3月中旬〜末、約12時間）

**目標: 開発の土台を整える。この後の全作業をcc-sddで進められる状態にする。**

#### Week 1（3/14〜3/21）: cc-sdd導入

| タスク                 | 詳細                                                                                                          | 時間 |
| ---------------------- | ------------------------------------------------------------------------------------------------------------- | ---- |
| cc-sdd インストール    | `npx cc-sdd@latest --lang ja` を実行                                                                          | 0.5h |
| Steeringファイル生成   | `/kiro:steering` でプロジェクト記憶を3ファイルに分割生成                                                      | 1h   |
| CLAUDE.md 整理         | cc-sddと重複する内容を整理。開発プロセスの記述を更新                                                          | 1.5h |
| 既存資産の廃止         | `.steering/` ディレクトリと `/add-feature` コマンドを削除                                                     | 0.5h |
| cc-sddワークフロー把握 | `/kiro:spec-init` → `spec-requirements` → `spec-design` → `spec-tasks` → `spec-impl` の流れを手を動かして理解 | 1.5h |

**生成されるファイル:**

```
.kiro/
├── steering/
│   ├── product.md    # プロダクトの目的・主要機能
│   ├── tech.md       # 技術スタック・設計方針
│   └── structure.md  # ディレクトリ構成・命名規則
└── specs/            # 機能ごとの仕様書（以降ここに蓄積）
```

#### Week 2（3/22〜3/28）: コード監査

| タスク                           | 詳細                                                                   | 時間 |
| -------------------------------- | ---------------------------------------------------------------------- | ---- |
| バイブコーディング箇所の洗い出し | コード全体を読んで「なぜこうなっているか分からない」箇所をリストアップ | 3h   |
| 監査レポート作成                 | 問題箇所・修正方針・優先度を `.kiro/audit.md` にまとめる               | 2h   |

**監査の観点:**

- 責務が不明確なモジュール（例: AuthServiceが大きすぎる）
- 削除予定の残留コード（例: X OAuth）
- 廃止するロール・権限（PREMIUM）
- 命名の一貫性
- 設計パターンの逸脱箇所

## cc-sddワークフロー（全開発の標準フロー）

```
新しい機能・修正が発生
  ↓
/kiro:spec-init "機能の説明"
  ↓
/kiro:spec-requirements → 人間が承認
  ↓
/kiro:spec-design → 人間が承認
  ↓
/kiro:spec-tasks → 人間が承認
  ↓
/kiro:spec-impl（タスク番号）→ TDD（RED→GREEN→REFACTOR）
  ↓
/kiro:validate-impl で整合性確認
  ↓
コミット（1 Todo = 1 Commit）
```

> **原則**: 承認なしに実装しない。「とりあえず作ってみる」はしない。
