# 完全移行計画 概要

mosaku アプリケーションをローカルDocker環境からクラウドネイティブ環境へ移行するための包括的な計画書です。

## 📊 移行の全体像

### 現在のアーキテクチャ
```
Docker Compose (ローカル)
├── Nginx (リバースプロキシ)
├── Frontend (React + Vite) :5173
├── Backend (NestJS + Prisma) :3000
└── PostgreSQL :5432
```

### 移行後のアーキテクチャ
```
クラウドネイティブ
├── Vercel (フロントエンド + CDN)
├── Google Cloud Run (バックエンド)
└── Supabase (PostgreSQL + Auth)
```

## 📅 推奨実行タイムライン

### **ステージ1: データベース基盤の移行**（3-4日、必須）

```
Day 1-2: Phase A (準備・セットアップ)
├── Supabase プロジェクト作成
├── ローカルデータベースのバックアップ
└── Prisma マイグレーションの適用

Day 2-3: Phase B (データ移行)
├── pg_dump または Prisma スクリプトでデータエクスポート
├── Supabase へデータインポート
└── データ整合性の検証

Day 3: Phase C (切り替え・テスト)
├── 環境変数を Supabase に切り替え
├── E2E テスト実施
└── パフォーマンステスト

Day 4: Phase D (クリーンアップ)
├── Docker Compose から PostgreSQL コンテナ削除
├── 環境変数クリーンアップ
└── ドキュメント更新
```

**成果物**: Supabase PostgreSQL が本番稼働

## 🔄 推奨実行順序

### **パターンA: 段階的移行（安全重視）**
```
Week 1: データベース移行 (Phase A-D)
  ↓
Week 2: バックエンドデプロイ (Phase C1-C6)
  ↓
Week 3: フロントエンドデプロイ (Phase V1-V6)
  ↓
Week 4-5: 認証移行 (Phase 1-5) ※オプション
```

**リスク**: 低

**期間**: 2-4週間

## 🛡️ リスク管理

### **データ損失リスク** ⚠️ 高
- **対策**: Phase A でローカルバックアップ必須
- **対策**: Phase B でデータ検証（レコード数、整合性）
- **対策**: Phase C で並行運用期間を設ける
- **ロールバック**: バックアップから復元（30分以内）

### **ダウンタイムリスク** ⚠️ 中
- **対策**: Phase C で環境変数切り替え時のみ再起動（1-2分）
- **対策**: Cloud Run のゼロダウンタイムデプロイ活用
- **対策**: Vercel のプレビューデプロイで事前検証
- **ロールバック**: Vercel/Cloud Run で前バージョンに即座に切り替え（1分以内）

### **コスト超過リスク** ⚠️ 低
- **対策**: Cloud Run の max-instances を設定（初期: 10）
- **対策**: Supabase 無料枠の使用状況を週次監視
- **対策**: Vercel Analytics でトラフィック監視
- **アラート**: 予算の80%で通知設定

### **認証エラーリスク** ⚠️ 中（認証移行時のみ）
- **対策**: Phase 3 で新旧認証の並行運用テスト
- **対策**: Phase 4 で段階的にエンドポイント切り替え
- **対策**: 既存ユーザーと Supabase ユーザーの紐付けテーブル
- **ロールバック**: 旧認証エンドポイントに戻す（環境変数で制御）
