## なぜ今これが要るのか

プロジェクトの最上流の判断軸は「**学びになるか × 使われるか**」（収益は目的ではなく制約）。
しかし現状、**「使われるか」を判定する定義がどこにも無い**。その結果:

1. `docs/project-plan-2026.md` のマイルストーンは「テーマ数」で組まれていたが、2026-06-20 に**和の4テーマへ集約**（量より質）を決定。**進捗を測る単位が消えたまま代わりが置かれていない**
2. `docs/progress.md` は **2026-06-20 を最後に停止**（約2ヶ月）。「今月何をもって前進としたか」を言語化できない状態
3. 実測（2026-08-12）: Cloud Run の直近2日のリクエスト 581 件のうち **568 件が UptimeRobot の `/health`**。実ユーザー起因は `/auth/refresh` 3 件のみ

→ **アウトプット指標（作った数）ではなくアウトカム指標（使われた度合い）が必要**。

## NSM: 週に3日以上メモを書いたユーザー数（W3W）

> **W3W = Weekly 3-day Writers**
> ある週において、**3日以上「書いた」ユーザーの人数**

### なぜ「書いた日数」なのか

Mosaku のブランドの核は「**人生という冒険を進めていく上で、道標になるようなものを書き留めておく場所**」。
価値は情報量でも滞在時間でもなく、**書く習慣が生活に入っていること**。よって指標も習慣を測る形にする。

### 却下した候補と理由

| 候補               | 却下理由                                                                                     |
| ------------------ | -------------------------------------------------------------------------------------------- |
| DAU / MAU          | 「開いた」だけでカウントされる。テーマを眺めただけの人と、道標を書き留めた人が同じ重みになる |
| 累計メモ数         | 累積値は減らないので**悪化を検知できない**。典型的な虚栄の指標                               |
| 総執筆文字数       | 長文＝価値ではない。道標は一行でも成立する。長文を書く人だけが正義になる歪みが出る           |
| 連続ストリーク日数 | 途切れた瞬間の罪悪感がプレッシャーになる。「内省の場」というブランドと正面から衝突する       |
| テーマ切替回数     | テーマは手段であって目的ではない。差別化軸ではあるが価値の代理変数にならない                 |

### なぜ「3日 / 週」なのか

- **1日/週**: 気まぐれと習慣が区別できない
- **7日/週**: 実質ストリーク。上記のとおりブランドと衝突し、達成者がほぼ出ない
- **3日/週 ≈ 隔日**: 「生活に入った」と言い切れる最小ライン。週末だけの人も、平日だけの人も拾える

### 「書いた」の厳密な定義

ある `userId` について、ある日（JST 0時区切り）に以下のいずれかが発生した場合、その日を**執筆日**とする。

- `Memo` が新規作成された（`createdAt` がその日）
- `Memo` の本文が実質的に変更された（`updatedAt` がその日）

補足:

- 自動保存は 2 秒デバウンスで `updatedAt` を頻繁に更新するため、**日単位で DISTINCT を取って丸める**（1日に何回保存しても1日）
- ゴミ箱送り（`trashedAt IS NOT NULL`）のメモも**執筆日としてカウントする**。書いた事実は消えないため
- ノートブックの編集は含めない。NSM は「メモを書いたか」に絞る（曖昧さを排除するため）

## 支える指標（NSM の分解）

NSM 単体では「なぜ増えた / 減った」が分からないので、3層に分解して見る。

| 層       | 指標                                   | 定義                                   | 何が分かるか                          |
| -------- | -------------------------------------- | -------------------------------------- | ------------------------------------- |
| 獲得     | **Activation 率**                      | 登録から7日以内に3日以上書いた人の割合 | 招待した人が立ち上がっているか        |
| 定着     | **W4 Retention**                       | 登録4週目に W3W だった人の割合         | 一過性で終わっていないか              |
| 深度     | **週間執筆日数の中央値**               | W3W ユーザーの週あたり執筆日数の中央値 | 3日ギリギリか、生活に食い込んでいるか |
| 劣化監視 | **自動保存エラー率 / Sentry エラー率** | 既存の Sentry から取得                 | NSM を追うあまり体験を壊していないか  |

> **カウンター指標を必ず併読すること。** 通知を増やす等でNSMだけ上げる打ち手は、この列が悪化するので検知できる。

## 計測方法（追加実装ゼロで出せる）

現行スキーマ（`Memo.userId` / `createdAt` / `updatedAt` / `trashedAt`）だけで算出可能。

```sql
-- 指定週（JST）の W3W を算出する
WITH writing_days AS (
  SELECT
    "userId",
    DATE(("updatedAt" AT TIME ZONE 'UTC') AT TIME ZONE 'Asia/Tokyo') AS jst_day
  FROM "Memo"
  WHERE "updatedAt" >= :week_start AND "updatedAt" < :week_end
  GROUP BY 1, 2
)
SELECT COUNT(*) AS w3w
FROM (
  SELECT "userId"
  FROM writing_days
  GROUP BY "userId"
  HAVING COUNT(DISTINCT jst_day) >= 3
) t;
```

```sql
-- ユーザー別の内訳（誰がどれくらい書いたか）
SELECT
  "userId",
  COUNT(DISTINCT DATE(("updatedAt" AT TIME ZONE 'UTC') AT TIME ZONE 'Asia/Tokyo')) AS writing_days,
  COUNT(*) AS save_events
FROM "Memo"
WHERE "updatedAt" >= :week_start AND "updatedAt" < :week_end
GROUP BY "userId"
ORDER BY writing_days DESC;
```

> `createdAt` 起因の執筆日を含めたい場合は `writing_days` を `createdAt` 版と `UNION` する。上記は自動保存が必ず `updatedAt` を更新する前提で簡略化している。

## 段階目標（いきなり数値目標は置かない）

現状の実ユーザートラフィックがほぼゼロである以上、最初にやるべきは**目標設定ではなくベースライン取得**。

### Phase A: 自分が使う（今〜）

> **オーナー自身が 4 週連続で W3W を満たす**

- これが達成できないうちは友人に配らない。**作者が書いていないアプリを他人が書き続けるはずがない**
- `docs/progress.md` が2ヶ月止まっている事実と、ドッグフーディングが実質停止している事実は同じ根を持つ
- `.kiro/steering/dogfooding.md` の金曜トリアージを再起動し、Friction Log を Mosaku 上で書くこと自体が W3W に効く

### Phase B: 友人に配る（Phase A 達成後）

> **W3W ≥ 5人 を 8 週間維持**

- 10〜20人に配って **5人が習慣化**すれば、定着率 25〜50%。個人開発のクローズドβとしては十分な合格ライン
- ここで初めて「使われている」と言い切れる

### Phase C: 課金を起動（Phase B 達成後）

> `monetization.md` の課金モデル v2 を実装する

- 課金基盤（`ai-billing-foundation`）が ⛔ 中止になっているのは、結果的に**順番として正しい**
- **使われている証明が先、課金の実装は後**。使われていないものに課金導線を作っても検証にならない

## 黒字ラインとの接続

2026-08-12 の実測に基づく（Cloud Run の `min-instances` を 1→0 に変更した後の数値）。

### 固定費

| 項目                          | 月額             | 備考                                                                                           |
| ----------------------------- | ---------------- | ---------------------------------------------------------------------------------------------- |
| Cloud Run                     | **約 ¥0**        | `min-instances: 0` 化により idle 課金が消滅。UptimeRobot の5分間隔ポーリングで実質ウォーム維持 |
| Supabase                      | ¥0               | 無料枠内                                                                                       |
| Vercel                        | ¥0               | Hobby                                                                                          |
| Resend / Sentry / UptimeRobot | ¥0               | いずれも無料枠内                                                                               |
| ドメイン（mosaku.jp）         | 約 ¥125          | 年額を12で割った概算                                                                           |
| **合計**                      | **約 ¥125 / 月** |                                                                                                |

> 変更前は Cloud Run が `min-instances: 1` で **月 ¥1,300〜1,500** を消費していた（実測: 1日 86,400 秒＝24時間フル課金）。

### 1ユーザーあたりの粗利

課金モデル v2（月 ¥500 で ¥500 ぶんの AI 込み、マージン ×1.5）より:

- AI を**使い切った**場合: 原価 ¥333 → **粗利 ¥167**
- AI を**使わなかった**場合: **粗利 ¥500**

### 損益分岐点

| ケース                       | 必要な有料ユーザー数                                        |
| ---------------------------- | ----------------------------------------------------------- |
| 最悪（全員が AI を使い切る） | **1人**（¥167 > ¥125）                                      |
| COMP 招待無料枠を n 人に配る | **有料 3n 人**（COMP 1人 = 月 ¥500 の持ち出し ÷ 粗利 ¥167） |

> **要点: COMP を1人配るごとに、有料ユーザーが3人必要になる。**
> `monetization.md` は COMP を「1人あたり最大 ¥1,500（3ヶ月）」と上限設計しているが、**同時に何人配れるか**の上限は未設計。Phase B で 10〜20人に COMP を配ると月 ¥5,000〜10,000 の持ち出しになる。ここは要決定事項。
