## 現状の実測（2026-08-13 コード調査）

**核心の問い: 「本番が壊れてから、自分が気づくまで何分か？」**
現時点の実測値は **最大 3 週間**（deploy-backend の失敗 cutover が P3009 でデッドロックしていた事件）。
このクールのゴールは **5 分**。

### 具体的な不整合（着手点そのもの）

- `backend/src/common/logger/app-logger.service.ts` — 全メソッドが `console.*` に素の文字列を流している。Cloud Run のログは `severity` フィールドを持たないので `severity>=ERROR` で絞り込めない
- `backend/src/memo/db-pool-observability.service.ts:97` — ここだけ 1 行 JSON を stdout に出している。**形式が 2 種類ある**
- `backend/src` 配下に `console.*` が 12 箇所、`AppLogger` 利用は auth / mail 系のみ
- `.github/workflows/deploy-backend.yml` に `if: failure()` の通知ステップが無い

## PdM 素養としての深掘りポイント

1. **DB 派生 vs イベント計測**: 現行は DB 派生（追加実装ゼロ）。限界は「開いたけど書かなかった」が見えないこと。**いつイベント計測に移行するか**の判断基準を自分で言語化する
2. **虚栄の指標を見抜く**: 累計メモ数を却下した理由（累積値は減らないので悪化を検知できない）を、他の指標にも適用できるようにする
3. **ゲートを守る**: Phase A 未達なのに Phase B（友人に配る）へ行きたくなる誘惑への対処。**段階を飛ばした瞬間に測定が意味を失う**

# 運用ルール

catchup-plan v2 と同じ。**外すと 3 度目の死が来る。**

1. **全項目に 5 分版がある。** 時間がない日はそれで「やった」判定。ゼロの日を作らないことが最優先
2. **各日が独立完結。** 3 日空いてもリハビリ回は不要。その日のメニューをそのまま出す
3. **時間がないと言われたら説得しない。** 即 5 分版に切り替える
4. **週末が潰れたらスキップして翌週へ。** 取り返さない
5. Claude は解説・出題・レビュー・進行管理のみ。実装コードは本人が書く
