# cc-sdd 社内導入戦略ドキュメント

作成日: 2026-02-28

## 背景・目的

- Claude Code を会社から1ヶ月契約で使用中
- 2ヶ月目の契約継続には効果の証明が必要
- 会社は **仕様駆動開発（SDD）の導入を検討中** → そこに焦点を絞る
- 別プロジェクトでは既に **cc-sdd (gotalab)** を使用している

---

## 対象プロジェクトの状況

| 項目             | 内容                                     |
| ---------------- | ---------------------------------------- |
| プロジェクト種別 | 既存プロジェクト（ブラウンフィールド）   |
| 開発チーム       | オフショアチーム                         |
| 要件定義チーム   | 日本チーム（ときには開発も担当）         |
| SDDネタ          | 新規機能は不明確、改修・バグ修正が現実的 |

### チーム構造とSDDの相性

```
日本チーム（要件定義）→ [仕様の曖昧さ] → オフショアチーム（実装）
```

SDDの仕様書がこの「曖昧なギャップ」を埋める成果物になる。
仕様書が日本↔オフショア間のコミュニケーション標準になれば、
手戻り・質問数・リードタイムの削減として数値化できる。

---

## 1ヶ月の戦略

### 採用した案：改修・バグ修正をSDDで回す

新機能がなくても、**小さな改修やバグ修正をSDDプロセスで回す**ことで
仕様駆動のサイクルを実証する。

#### バグ修正版のコマンドフロー（既存プロジェクト向け）

```
steering         → 現在のコードベースを分析・理解
spec-init        → 修正案件の仕様プロジェクト初期化
validate-gap     → 仕様と現状のギャップ確認
spec-requirements → バグの根本原因・再現条件・修正方針の合意
spec-design      → 具体的な修正箇所・影響範囲の設計
spec-tasks       → 実装・テスト・確認のタスク分解
spec-impl        → オフショアへの指示書として渡す
```

#### 各フェーズの読み替え

| cc-sddコマンド      | バグ修正文脈での意味                     |
| ------------------- | ---------------------------------------- |
| `spec-requirements` | バグの根本原因・再現条件・修正方針の合意 |
| `spec-design`       | 具体的な修正箇所・影響範囲の設計         |
| `spec-tasks`        | 実装・テスト・確認のタスク分解           |
| `spec-impl`         | オフショアへの指示書として渡す           |

#### 良い対象案件の選び方

- 1〜2週間以内に修正〜確認まで完結する
- 原因が曖昧で「なんとなく直した」になりがちな案件
- オフショアに渡す予定がある（効果が検証しやすい）

---

## 計測・効果証明の方法

### 記録すること

| 指標                   | Before（今まで） | After（SDD導入後） |
| ---------------------- | ---------------- | ------------------ |
| オフショアからの質問数 | 過去実績を参照   | 同条件で比較       |
| 手戻り回数             | 過去実績を参照   | 同条件で比較       |
| 修正〜承認までの日数   | 過去実績を参照   | 同条件で比較       |
| 仕様の認識齟齬件数     | 過去実績を参照   | 同条件で比較       |

### 会社への説明フレーム

```
「本来X日かかるはずの手戻りが、仕様書の事前合意でY件防げた」
「オフショアへの質問数がN件からM件に減った」
「SDDはClaude Codeがなくても同じフローを維持できる設計になっている」
```

最後の点が重要：**SDD採用の判断とClaude Code継続の判断を切り離して説明できる**。

## cc-sdd 概要

### リポジトリ

[gotalab/cc-sdd](https://github.com/gotalab/cc-sdd)

### インストール

```bash
cd your-project
npx cc-sdd@latest --claude --lang ja
```

### コアコマンド一覧

| コマンド                  | 内容                         |
| ------------------------- | ---------------------------- |
| `/kiro:spec-init`         | 仕様プロジェクト初期化       |
| `/kiro:spec-requirements` | 要件定義書生成（EARS形式）   |
| `/kiro:spec-design`       | 設計書生成（Mermaid図付き）  |
| `/kiro:spec-tasks`        | タスク分解（依存関係追跡）   |
| `/kiro:spec-impl`         | 実装実行                     |
| `/kiro:steering`          | 既存コード分析（既存PJ必須） |
| `/kiro:validate-gap`      | 仕様と現状のギャップ検証     |
| `/kiro:validate-design`   | 設計の実装可能性検証         |

### 生成ファイル構成

```
.kiro/
└── specs/
    └── {機能名・案件名}/
        ├── requirements.md   # 要件（EARS形式）
        ├── design.md         # 設計（Mermaid図付き）
        └── tasks.md          # タスクリスト（依存関係付き）
```

### 新規 vs 既存プロジェクトのフロー

**新規（グリーンフィールド）:**

```
spec-init → spec-requirements → spec-design → spec-tasks → spec-impl
```

**既存（ブラウンフィールド）← 今回のケース:**

```
steering → spec-init → validate-gap → spec-design → validate-design → spec-tasks → spec-impl
```

### 他ツールとの比較

| 観点             | mosaku独自SDD                 | cc-sdd                               |
| ---------------- | ----------------------------- | ------------------------------------ |
| セットアップ     | Gitで管理するカスタムファイル | `npx`一発・30秒                      |
| 仕様フォーマット | 自由                          | EARS形式（標準化）                   |
| 設計書           | Markdown                      | Mermaid図付き                        |
| ギャップ検証     | なし                          | `validate-gap`で明示的に実施         |
| 対応ツール       | Claude Code専用               | Claude Code, Cursor, Gemini CLI等8種 |
| チーム展開       | 手動                          | `npx`一発                            |
